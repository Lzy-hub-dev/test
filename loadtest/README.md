# 只读压测流程

面向"先走一遍流程、不碰写入"的场景。所有脚本只发 GET 请求，不产生订单、不扣余额、不改状态。

## 一、为什么只能压这几类接口

| 接口类型 | 能否压 | 原因 |
|---|---|---|
| 静态资源（`/`、JS、CSS） | ✅ 放心压 | 纯读取，无状态 |
| 匿名只读 API | ✅ 可压 | 无身份、无副作用 |
| 验证码 `/captchaImage` | ⚠️ 可控 | 会在 Redis 写一个 2 分钟过期的键，无业务数据 |
| 登录 | ⚠️ 谨慎 | 写登录日志、签发 token |
| 下注 / 抽奖 / 充值 / 提现 | ❌ 禁止 | 产生真实资金流水，账本会被污染 |

**当前可达的目标（实测）**

| 目标 | 地址 | 说明 |
|---|---|---|
| 玩家端静态站 | `https://109.123.233.208/` | 直连源站，走默认 vhost，返回 SPA |
| 后台后端 | `https://admin.pai.casino/prod-api/` | RuoYi，匿名可达 |
| 玩家端 API | `https://api.pi.casino/api/` | **被 Cloudflare 403 拦**，直连源站也 403（只允许 CF 回源） |

玩家端 API 压不了，这是网络策略导致的，不是脚本问题。要压它需要在服务器上本机发起，或给测试机加白名单。

## 二、四步流程

### 第 0 步：冒烟（10 秒）

目的只有一个：确认脚本写对了、目标通了、断言没错。**不产生压力**。

```bash
cd E:/projects/test/loadtest
../k6/k6.exe run smoke.js
```

期望：`checks_succeeded 100%`。如果有断言失败，先修脚本，别急着加压。

### 第 1 步：基线（2 分半）

低并发跑稳态，拿到"系统空闲时正常多快"。这个数字是后面所有对比的参照。

```bash
# 静态前端
../k6/k6.exe run static-baseline.js

# 后台后端（轻量，只打根路径）
ADMIN_BASE=https://admin.pai.casino ../k6/k6.exe run admin-readonly.js

# 后台后端（含验证码，有实际计算量）
ADMIN_BASE=https://admin.pai.casino CAPTCHA=1 ../k6/k6.exe run admin-readonly.js
```

### 第 2 步：阶梯加压（找拐点）

并发按 20 → 50 → 100 → 200 递增，每档跑 2 分钟。观察 **RPS 是否还在涨**：

- RPS 随并发线性上涨 → 还有余量
- RPS 停滞但延迟上升 → 到拐点了，这就是容量上限
- 延迟上升且失败率 > 1% → 已经过载

改 `stages` 里的 `target` 即可，不用改逻辑。

### 第 3 步：峰值（可选）

用拐点值的 1.2 倍压 3 分钟，看恢复能力：压力撤掉后延迟是否回到基线。回不去说明有资源泄漏（连接池、线程、内存）。

## 三、结果怎么看

跑完终端会打印一张表，重点看四个：

| 指标 | 含义 | 健康值 |
|---|---|---|
| `http_req_duration p(95)` | 95% 请求的响应时间 | 静态 < 800ms，API < 1s |
| `http_reqs` | 每秒完成请求数（RPS） | 越高越好，但要结合延迟 |
| `http_req_failed` | 失败率 | < 1% |
| `iteration_duration` | 单轮完整耗时 | 用于判断瓶颈在请求还是等待 |

阈值写在脚本的 `thresholds` 里，没达标时 k6 会打 `level=error msg="thresholds ... have been crossed"` 并以非 0 退出码结束 —— 这是**判据**，不是报错。

## 四、三个容易踩的坑

**① 代理变量会把流量带偏**

本机有全局 `HTTPS_PROXY`，k6 会跟着走代理，压测对象就变成了代理而不是你的服务器。运行时必须剥掉：

```bash
env -u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy ../k6/k6.exe run xxx.js
```

**② 直连 IP 必须跳过证书校验**

证书签的是域名，直连 IP 会域名不匹配。脚本里已设 `insecureSkipTLSVerify: true`。

**③ 首次运行会偏慢**

第一次跑常有 TLS 握手、DNS、连接池冷启动的开销，数据会明显高于后续。判断基线时用**第二次**的结果。

## 六、实测记录（2026-11-16，本机发起）

| 项目 | 结果 |
|---|---|
| 冒烟 `smoke.js` | 35/35 断言通过，avg 160ms，p95 208ms |
| 静态基线 `MAX_VUS=20` | 1,024 请求 / 7.1 RPS，p95 2.14s，失败率 **4.2%** |
| 静态基线 `MAX_VUS=5` | 253 请求 / 1.7 RPS，p95 663ms，失败率 **4.3%** |
| 并发 curl ×10 | 10/10 成功，connect 约 1ms |
| 并发 curl ×20 | 20/20 成功 |

**结论：本机不适合当压测发起端。**

失败模式是 `conn=0 wait=15000`（连接未建立就超时）和 `EOF`，属于连接层被丢弃，不是应用慢。
curl 并发 20 全成功、k6 在 5 并发就丢 4%，差异出现在 k6 的连接建立环节；本机存在透明代理层
（`ping` 到目标 0ms、`connect` 1ms 均为本地拦截特征），对 k6 的并发连接不稳定。

因此上表的 RPS / p95 **不能用于判断服务器容量**，只能证明脚本与链路可用。
要测真实容量，须在服务器本机或同机房机器上发起。

### 服务器本机执行方式

```bash
# 在服务器上跑，直接打 127.0.0.1，绕开网络与代理
cd /path/to/k6
./k6 run loadtest/static-baseline.js -e STATIC_BASE=http://127.0.0.1:80
./k6 run loadtest/admin-readonly.js -e ADMIN_BASE=http://127.0.0.1:8239 -e CAPTCHA=1
```

本机压本机时 `insecureSkipTLSVerify` 无所谓，走 http 即可，测出来的是纯应用能力。

## 七、顺手发现的两件事

1. **gzip 是开的**：`/` 未压缩 18,957 B → gzip 后 6,195 B（约 3 倍）。但 k6 默认不带 `Accept-Encoding`，
   第一轮基线白拉了三倍流量。脚本已补上该头。
2. **`/prod-api/` 仍返回「RuoYi 后台管理框架，当前版本：v3.9.0」** —— 说明上次的源码加固
   （移除版本横幅、关闭匿名 actuator 等）**还没有部署到生产**。压测前建议先确认这一点，
   否则压的是旧代码。
